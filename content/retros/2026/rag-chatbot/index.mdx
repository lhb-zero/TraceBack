## 项目概述

为公司内部搭建基于企业文档的智能客服系统。用户上传 PDF/Markdown 文档后，系统能对员工提问进行精准回答。最终实现了 85% 的问题命中率，部署在内部服务器供 50+ 人使用。

## 技术要点

- **向量数据库选型**：选择 ChromaDB 而非 Pinecone，因为是内部部署、数据量不大（<10万条），ChromaDB 零运维成本
- **Chunk 策略**：从固定 512 token 切分改为按段落语义切分 + 重叠窗口，召回率提升约 20%
- **检索增强**：引入 Hybrid Search（向量 + BM25 关键词），解决纯向量检索对专有名词不敏感的问题
- **Prompt 工程**：设计了 system prompt 模板，强制模型在回答时引用来源文档段落

## AI 协作记录

- AI 生成了基础的 LangChain chain 代码框架，我在此基础上重写了 retriever 部分（因为默认的 similarity search 不满足需求）
- Prompt 模板的初版由 AI 生成，但发现模型经常"编造"不存在的文档内容，我增加了"如果上下文中没有相关信息，明确说不知道"的约束
- **理解验证**：RAG 的核心不是"让模型更聪明"，而是"给模型正确的上下文"。检索质量决定了上限，模型能力只决定表达质量

## 踩坑与解决

- ChromaDB 持久化路径在 Docker 中权限报错 → 挂载 volume 时指定 uid
- LangChain 0.1 → 0.2 升级后 Memory 接口完全不兼容 → 锁定版本，写迁移脚本
- 中文文档 chunk 后语义碎片化严重 → 改用 jieba 分词辅助断句

## 我学到了什么

- RAG 系统 80% 的功夫在检索侧（chunk、embedding、检索策略），而非生成侧
- "先评估再优化"比"凭感觉调参"效率高 10 倍，接入 Ragas 评估框架后优化方向一目了然
- LangChain 的抽象层在快速原型时有用，但生产环境需要理解底层逻辑才能调优
